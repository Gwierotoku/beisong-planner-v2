# 背诵规划表重构方案（时间预算驱动调度）

> 目标：把「按固定复习日期生成待办清单」改造成「以用户每天可投入的时间预算为约束、由程序动态安排最有价值任务」的学习调度系统。本文对应需求文档的「第一阶段：现有项目分析」和「第二阶段：架构设计」，实施与验证结果见文末与 README。

## 一、现有项目分析

### 1. 架构现状

| 文件 | 作用 |
| --- | --- |
| `index.html` | 页面骨架：4 个视图（今日复习 / 条目管理 / 科目设置 / 数据备份） |
| `app.js` | 单文件 IIFE，约 2300 行，包含数据模型、存储、排期算法、全部渲染与交互 |
| `styles.css` | 平面风样式、响应式布局、A4 打印分页 |

- 纯前端、无构建步骤、无第三方依赖，数据存 `localStorage`（键名 `beisong-plan-v1`）。
- 业务逻辑与 DOM 渲染、事件处理混在同一个 IIFE 中，算法函数（`buildPlan`、`pendingSession`）与界面函数互相直接读取全局 `state`。

### 2. 当前复习任务生成逻辑

- 首次背诵当天记为第 1 天，第 n 次安排在第 `1.7^(n-1)` 天（四舍五入），上限 4 年 / 14 轮。
- 第 n 次建议用时 = `firstMinutes / √n`。
- 条目只保存一个「已完成轮次 → 完成日期」的映射 `done`；「下一次任务」由「第一个未完成的计划轮次」推导。
- 今日清单 = 所有条目中「计划日期 ≤ 查看日期且未完成」的第一个未完成轮次，按逾期天数、计划日期、名称排序，按科目分组分页打印。
- 逾期任务永久保留并标注逾期天数，没有预算上限、没有优先级、没有延期策略、没有执行耗时与回忆结果的区分。

### 3. 当前数据结构及不足

```json
{
  "version": 1,
  "subjects": [{ "id": "s1", "name": "英语", "color": "#d9e7f2", "archived": false }],
  "entries": [{ "id": "e1", "name": "单词 Unit 1", "subjectId": "s1",
                "firstDate": "2026-10-24", "firstMinutes": 20,
                "done": { "1": "2026-10-24", "2": "2026-10-25" }, "prepared": false }],
  "settings": { "cols": 3 }
}
```

不足：

1. 没有时间预算概念，任务清单只受「到期」约束。
2. `done` 只记录完成日期，丢失实际耗时、回忆效果、执行类型，无法支撑动态间隔与耗时估计。
3. 复习间隔是硬编码公式，无法按记忆表现调整。
4. 预计用时只由首次用时推导，无法根据历史执行数据修正。
5. 没有「原始建议日期 / 动态安排日期 / 实际完成日期」的区分。
6. 条目没有重要程度、难度、暂停/归档状态，无法参与优先级计算。
7. 没有任何「计划解释」信息，用户不知道任务为何被安排或延期。
8. 所有逻辑耦合在 UI 文件中，无法单元测试。

### 4. 新旧调度逻辑区别

| 维度 | 旧逻辑 | 新逻辑 |
| --- | --- | --- |
| 任务来源 | 固定公式日期，到期即列入清单 | 到期任务 + 新内容队列，进入候选池 |
| 是否受时间约束 | 否，清单无限增长 | 是，科目专属预算 + 全局通用预算 |
| 排序 | 逾期天数 → 日期 → 名称 | 综合优先级（逾期、重要度、遗忘风险、失误、考试临近） |
| 延期 | 无（一直挂在清单里） | 按间隔比例容忍 2–14 天，超出优先强制安排，但最多超出当天可用预算 25% |
| 单次时长 | 固定公式 | 公式作为先验，用实际耗时修正，再按回忆结果调整，限制在首次用时的 1/4–2 倍 |
| 间隔 | 固定 1.7 倍 | 表格化基准（1、2、4、10 天……最长 300 天），按上次回忆结果乘倍率 |
| 完成记录 | 只记日期 | 独立执行记录：实际耗时、回忆结果、难度、预算来源 |
| 计划稳定性 | 稳定但不可解释 | 每次打开重算（确定性），历史记录不可变，任务不会重复创建 |
| 未来负载 | 无 | 7～21 天模拟预测，提前暴露缺口 |

## 二、新架构

按职责拆分模块，全部为无依赖的浏览器经典脚本（`file://` 可直接打开），同时可在 Node 中加载做单元测试；命名空间挂在 `window.BS`。

| 文件 | 职责 |
| --- | --- |
| `js/core.js` | 日期、数值、格式化、转义等纯工具 |
| `js/model.js` | 数据结构、校验、v1→v2 迁移、localStorage 读写、示例数据 |
| `js/review.js` | 理论复习轮次、调整后间隔、条目记忆状态推导（纯函数） |
| `js/duration.js` | 预计耗时估计（理论值 + 实际数据平滑修正） |
| `js/priority.js` | 任务综合优先级、新内容优先级、考试临近度 |
| `js/budget.js` | 每周模板、标签模板、日期覆盖、预算解析、实际用量核算 |
| `js/scheduler.js` | 候选任务收集、单日预算调度、分配与未安排原因 |
| `js/forecast.js` | 多日模拟：逐日调度、延期传递、缺口预测 |
| `js/app.js` | 渲染、表单、事件、打印（只调用上述模块） |
| `tests/run-tests.js` | Node 单元测试（日期、预算、调度、间隔、耗时、迁移、预测） |

```json
  "meta": { "createdAt": "...", "migratedFrom": 1, "migratedAt": "...", "notice": "" },
  "subjects": [{ "id": "s1", "name": "数学", "color": "#d9e7f2", "archived": false, "createdAt": "..." }],
  "entries": [{

  "settings": {
    "newContentEnabled": true, "newContentDailyLimit": 3,
    "forecastDays": 14
  }

```

关键设计：

- **条目（Entry）**只保存稳定信息；记忆状态、间隔、到期日、预计耗时由 `logs` **实时推导**，撤销记录后状态自动回退。撤销或迁移恢复的下一轮任务通过 `entry.pendingTask` 固定原到期日，完成后自动清除，避免按新规则把过去的任务推到未来。
- **执行记录（Log）**一次执行一条，实际耗时与回忆结果分开记录，并保留当时的计划用时、原始到期日、动态安排日、预算分摊。
- **预算（Budgets）**= 每周默认模板 + 标签模板 + 日期覆盖。日期覆盖保存的是「标签预算的副本」（`origin: "label"`），用户改动后为 `origin: "manual"`；修改/删除标签模板不会改动已应用日期的预算。
- **新内容**：`firstDate = null` 表示「首次学习日期由系统按预算安排」，进入新内容候选队列；`firstDate` 为未来日期表示预备诵。
- **状态**：条目 `active / paused / archived`；任务层状态由推导 + 当日调度结果得出（待复习、今日待复习、已逾期、已延期、已安排、待补救、已完成）。

### 预算解析优先级

1. 日期覆盖（用户手动调整或已应用标签的副本）
2. 每周默认预算（按 ISO 星期 1–7）
3. 都没有 → 0 分钟（系统不假设用户有时间）

科目任务先用本科目专属预算，不足部分申请通用预算；专属预算剩余不转移给其他科目。通用预算是一份全局余额，调度时逐笔扣减，保证不会重复占用。

### 实际用量 vs 计划用量

- 调度阶段：任务只占用「计划预算」，未执行不计入实际。
- 完成时：按 `min(实际耗时, 本科目剩余专属预算)` 先记专属，其余计入通用预算；实际超出预算时明确显示超支。
- 每日「实际使用时间」只来自执行记录的 `actualMinutes` 之和。

## 四、核心算法

### 1. 间隔调整（`review.js`）

- 理论间隔表（表格化）：第 1 天首次、第 2 天、第 4 天、第 10 天、第 20 天……前期间隔为 1、2、6、10 天，之后约按 1.7 倍增长；长间隔压缩到最长 300 天。共 13 轮，最后一轮约第 1179 天。
- 调整间隔：`new = theoryNext × recallFactor`；不累积历史偏差，只参考上一次回忆结果。
- `recallFactor`：顺利 2.0、正常 1.0、困难 0.55；失败不排常规复习，安排第二天补救。
- 回忆失败：下一次任务是「补救学习」，安排在第 2 天；补救完成后第二天重做失败的那一轮，成功后才进入下一轮；补救仍失败则继续顺延补救。同一轮连续失败 3 次会回退一轮。
- 部分完成（`partial`）不推进轮次，只记录实际用时。
- 延期只影响「动态安排日期」，不改变间隔，除非用户真的完成了复习并记录了结果。
- 延迟容忍：`clamp(round(间隔/6), 2, 14)` 天；1 个月约 5 天。

### 2. 耗时估计（`duration.js`）

- 先验：`firstMinutes / √n`，并仅在无历史时用初始难度做 ±20% 修正。
- 修正：取最近 8 条执行记录的 `实际 / 计划` 比值，按时间加权 EWMA（α=0.4），并用 `样本数/(样本数+2)` 收缩，单条比值限制在 0.25–4。
- 再乘上一次回忆倍率：顺利 0.8、正常 1.0、困难 1.3、失败 2.4。
- 最终下限为首次用时的 1/4，上限为首次用时的 2 倍，并限制在 0.5–240 分钟。
- 因预算不足被压缩安排（`partial`）的记录不参与耗时修正，也不推进轮次，避免「压缩安排 → 实际用时变小 → 预计用时被低估 → 安排更多」的反馈循环；用户明确选择完整完成时才按正常记录推进。
- 实际耗时只影响耗时基准，回忆结果影响倍率，二者不混用。

### 3. 优先级（`priority.js`）

```text
分数 = 延期紧迫 (min(1, 延期/可延迟) × 30，超过可延迟再加 10)
     + 重要程度 ((importance-1)×5，0–20)
     + 遗忘风险 (min(1,(延期+0.5)/max(1,间隔))×12)
     + 失误累积 (min(lapses,3)×4) + 补救任务 15
     + 首次学习任务 8
     + 考试临近 (0/6/12/18)
```

- 延期越久、间隔越长、失误越多，分数越高；同分按原始到期日、名称排序。
- 新内容使用独立分数：`(importance-1)×6 + 等待天数×1.5 + 5`；只在到期任务安排完后使用剩余预算，并按科目判断：只有「本科目还有到期任务未安排」时才冻结该科新内容。

### 4. 单日调度（`scheduler.js`）

1. 解析当日预算，扣除已完成任务的实际用量，得到剩余专属预算与剩余通用预算。
2. 收集候选任务：所有未完成条目的下一个任务（学习 / 复习 / 补救），以及新内容队列。
3. 到期任务（原始建议日期 ≤ 当天）参与调度；未到期任务默认不提前，只有「困难/失败过、间隔至少 2 天」且预算空闲时才进入提前复习。
4. 第一轮：超过各自可延迟天数的任务优先强制安排；强制部分最多使用当天可用预算的 1.25 倍，休息日/考试日可关闭强制，超出部分进入未安排。
5. 第二轮：其余到期任务按优先级降序，逐个从「专属 → 通用」扣减预算；预算不够全额时允许压缩，但压缩后的单次时长不少于 3 分钟，并标记 `partial`；任务本身预计不足 3 分钟时按全额安排。
6. 第三轮：没有未安排的到期任务时，用剩余预算安排提前复习（可在设置关闭）。
7. 第四轮：按新内容优先级启动新内容；只冻结还有到期任务未安排的科目，其他科目仍可使用自己的预算，受每日条数上限约束。
8. 记录未安排任务、缺口分钟数、原因（预算不足 / 强制上限 / 休息日关闭强制 / 等明天 / 已逾期）。
9. 输出警告：强制安排、强制上限、休息日关闭强制、预算超支、未安排任务、当天预算为 0。

调度是**纯函数**：同一份数据、同一天、同一预算，结果确定；任务身份由「条目 + 轮次 + 类型」唯一确定，不会重复创建，也不需要保存任务表。

### 5. 未来负担预测（`forecast.js`）

- 从今天（或指定日期）开始，逐日模拟：用当日预算调度「已到期 + 前一日未安排」的任务。
- 已安排的任务视作那天完成，并按「正常回忆」继续生成后续复习（新内容和已有条目都适用），未安排的继续传递并自然提高延期等级。
- 新内容每日按上限参与，模拟其占用和后续复习负担。
- 输出每天：各科目任务数 / 预计分钟、总预算、缺口、延期任务数、警告；并给出整体「最紧张的一天」。

## 五、数据迁移（v1 → v2）

1. 读取顺序：`beisong-plan-v2` → 若不存在再读 `beisong-plan-v1`；v1 原始键**保留不删**，新数据写入 v2 键。
2. 旧 `entries[].done` 迁移为执行记录：
   - `done["1"]` → `type: "learn"` 记录，日期为完成日期；
   - `done[n]`（n≥2）→ `type: "review"`、`round: n` 记录，实际/计划耗时取当时的公式估计，回忆结果记为 `normal`；
   - 记录 ID 固定为 `legacy-learn-<entryId>`、`legacy-review-<entryId>-<n>`，重复导入/加载不会产生重复记录。
3. 旧数据没有预算：迁移时按「每个科目 20 分钟 + 通用 20 分钟」生成每周默认预算，并在数据页提示用户调整；标签/日期覆盖为空。
4. 旧 `prepared` 语义保留：首次日期在未来 → 预备诵；首次日期在过去且没有 `done["1"]` → 自动补一条首次学习记录（与旧版行为一致）。
5. 旧字段 `done` 保留在 `entry.legacyDone` 中，导出备份仍然包含，绝不覆盖。
6. 迁移时为每个条目保留「下一轮的旧版原始计划日期」，写入 `entry.pendingTask`；已排好的下一轮不按新版间隔改写，完成这一轮之后才按实际表现和动态间隔重算。旧日志的 `dueDate` 使用原来的理论日期，撤销时据此恢复任务。
7. 已经被旧重构版本导入过的 v2 数据，通过 `meta.pendingPinned` 做一次性的同规则补处理，并在今日页提示「保留旧计划」或「改用新规则重排」；选择后不再重复提示。之后新增条目不再固定旧日期。
8. v1 备份 JSON 可直接导入，走同一迁移函数。

- 新增「预算与标签」页：每周默认预算表、日期预算（应用标签/手动覆盖/恢复默认/是否允许强制）、标签模板管理、未来 14 天预算一览、新内容与提前复习设置。
- 新增「负担预测」页：7/14/21 天预计负担、缺口与延期提示。

- 条目页：重要度、难度、状态、调整后的间隔与预计耗时；详情页展示学习记录、理论日期 vs 动态日期、延迟容忍、纠错（撤销）。
- 数据页：完整的「复习节奏表」（轮次、距首次天数、基准间隔、公式用时、最长可延迟），并解释间隔倍率、延迟容忍和用时上下限。
- 保持原有视觉风格、打印布局与分页逻辑；打印只输出今日任务清单。

## 七、测试计划

Node 单元测试覆盖：

- 日期：跨月/闰年/星期计算。
- 预算：每周模板、日期覆盖优先级、标签复制语义、标签模板修改不影响已应用日期、删除标签保留预算、专属预算不转移、通用预算共享与耗尽。
- 调度：预算充足/不足/为零、部分压缩、强制上限、休息日关闭强制、提前复习、按科目冻结新内容、未安排原因、通用预算不重复占用、任务不重复。
- 间隔：顺利/正常/困难/失败、上下限、失败不推进轮次、补救后重做、连续失败回退、部分完成不推进。
- 耗时：实际偏快/偏慢、单次异常、样本不足、压缩记录不参与修正。
- 迁移：v1 导入、幂等、预备诵、旧字段保留、迁移提示与改用新规则。
- 预测：缺口、延期传递、标签预算生效、后续复习链式模拟。
- 一致性：完成记录后重新调度不重复、撤销后恢复原到期日、迁移保留旧计划日期。

实际结果：82 项单元测试全部通过；无头 Edge 冒烟测试完成全部视图渲染、完成记录、调度解释、标签表单、条目详情、预测卡片、部分完成和迁移重排等交互，无运行时错误；60 条任务打印为 2 页 PDF。

## 八、取舍与已知限制

1. 提前复习只针对「困难/失败过、且间隔至少 2 天」的内容，默认最多提前 1 天，可在设置里关闭或改成 2–3 天；不会把所有未来任务都拉到今天。
2. 考试临近是全局启发式（按日期标签 `kind = exam/preExam` 判断），不做「某科目某考试」的精细映射。
3. 调度结果每次打开重算，不保存历史计划快照；因此查看过去日期时看到的是「按当前数据重算」的视图，历史执行记录本身不可变。
4. 预测中的后续复习按「正常回忆」推演，真实结果会因顺利/困难/失败而变化，预测是负担提示而不是承诺。
5. 预算以分钟为单位，最小调度粒度为 0.1 分钟；任务被压缩时单次不少于 3 分钟，预计用时本身不足 3 分钟的任务仍会全额安排。
6. 旧版「自动跳过已过去轮次」不再伪造复习记录，改为保留首次学习记录并让下一次复习立即进入待办。
7. 默认节奏固定为 13 轮、最长间隔 300 天、延迟容忍最多 14 天；这些是产品默认值，可在 `review.js` 中调整。
8. 预计用时下限为首次用时的 1/4、上限为 2 倍；非常难或非常简单的条目会触及边界，不会无限变化。
